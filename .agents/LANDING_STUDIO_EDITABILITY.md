# SYSTEMIFY / LANDING STUDIO — FULL EDITABILITY DIRECTIVE
## Controlled Full-Page Editing Without Breaking the Design System

> **Status:** REQUIRED / OPEN IMPLEMENTATION
> **Repository:** `Ridzz05/mify-id`
> **Scope:** Public landing page + Site Studio + shared renderer + persistence schema
> **Priority:** Complete content ownership from Admin, constrained by Systemify design rules
> **Completion Rule:** This directive MUST NOT be marked complete while meaningful public-facing landing content still requires source-code editing.
>
> This document supersedes any previous interpretation of Landing Studio as a “selected property editor”.
>
> The intended product is:
>
> # A CONTROLLED FULL-PAGE EDITOR
>
> not a free-form page builder,
> not a partial hero customizer,
> and not a source-code-assisted CMS.

---

# 00 / THE NON-NEGOTIABLE GOAL

After this implementation, an authorized admin must be able to modify **all meaningful human-visible landing-page content and supported presentation decisions from Site Studio without editing source files**.

That includes:

- headings
- eyebrow labels
- supporting copy
- CTA labels
- CTA targets when explicitly allowed
- section visibility
- ordered list items
- capability items
- process steps
- before/after rows
- principles
- contact text
- form labels
- form placeholders
- success-state copy
- evidence-section presentation settings
- supported alignment presets
- supported shape presets
- supported motion presets
- supported responsive visibility
- supported secondary hero objects
- ordering where explicitly supported

The admin MUST NOT need to open:

- `Welcome.jsx`
- `LandingRenderer.jsx`
- localization source files
- Tailwind config
- CSS files
- PHP source
- React source

to change ordinary public-facing landing content.

# 01 / CURRENT IMPLEMENTATION GAP

The current implementation provides a strong foundation:

- shared public/preview renderer
- semantic configuration
- draft vs published state
- revision history
- server-side normalization
- hero content controls
- hero layout controls
- hero highlight controls
- global shape presets
- GSAP semantic motion presets
- responsive preview

However, the current editor is still **partially source-owned**.

Several sections expose only:

- `eyebrow`
- `title`
- `intro`
- `visible`

while meaningful repeated content remains hard-coded in the renderer or static content objects.

This directive exists to close that gap.

---

# 02 / NEW DEFINITION OF “EDITABLE”

A section is NOT considered editable merely because its title can change.

A section is considered editable only when all meaningful content units inside it are controlled by configuration or an explicitly separate admin-owned data source.

## NOT ENOUGH

Process section:

- editable section title
- hard-coded process steps

Result:

> NOT FULLY EDITABLE

## CORRECT

Process section:

- editable section title
- editable process steps
- add step
- remove step
- reorder step
- edit number
- edit label
- edit description

Result:

> FULLY EDITABLE

# 03 / SOURCE-OWNERSHIP RULE

Every public-facing value belongs to exactly one of these categories:

## A. SITE STUDIO OWNED

Editable through Landing Studio.

Examples:

- marketing copy
- headlines
- CTA labels
- process copy
- principles
- capability names
- service items
- contact copy
- presentational choices

## B. DOMAIN-DATA OWNED

Managed through another dedicated admin module.

Examples:

- Portfolio projects
- Client case studies
- Published project evidence
- Project URLs
- Portfolio screenshots

The Landing Studio may control how these records are presented,
but it should not duplicate their canonical business data.

## C. IMMUTABLE SYSTEM UI

Intentionally fixed application language.

Examples may include:

- Save Draft
- Publish
- Revision
- validation messages generated by the application
- inaccessible implementation metadata

This category MUST be small.

Do not classify ordinary website copy as “system UI” merely to avoid implementing an editor.

---

# 04 / COMPLETION GATE

Codex MUST NOT mark this directive complete until all of the following are true:

1. Every landing section has an inspector.
2. Every meaningful repeated content unit is editable or explicitly domain-data owned.
3. Every editable repeated unit supports the required add/remove/reorder behavior.
4. Public landing and preview use the same renderer.
5. Draft edits remain private.
6. Publish updates the public page.
7. Revision restore preserves the complete configuration.
8. JavaScript normalization preserves every supported field.
9. PHP normalization preserves and validates every supported field.
10. Automated tests cover the complete config shape.
11. A hard-coded content audit has been completed.
12. No meaningful business/marketing copy remains hard-coded in the renderer unless documented as intentionally immutable.

# 20 / CONFIG MIGRATION RULE

Existing published configuration must not break.

Implement backward-compatible normalization.

Requirements:

1. Existing version 1 data loads.
2. Missing version 2 fields receive defaults.
3. Existing published site remains visually stable after migration unless intentionally changed.
4. Publishing new config writes version 2.
5. Existing revisions remain restorable.

Do NOT destroy previous revision compatibility.

---

# 21 / JAVASCRIPT NORMALIZER

`resources/js/Pages/Landing/config/schema.js`
must preserve and validate the complete V2 configuration.

It must NOT silently discard newly editable fields.

Every new field must be:

- normalized
- allowlisted where enum-based
- bounded where text-based
- array-validated where structural
- assigned stable IDs where required

A UI control without matching normalization is considered incomplete.

---

# 22 / PHP NORMALIZER

`App\Support\LandingConfiguration`
must mirror the frontend schema.

Every field supported by JavaScript must also be supported by PHP.

Server normalization is the authority before persistence.

Requirements:

- enum allowlists
- boolean coercion rules
- bounded strings
- bounded list lengths
- sanitized IDs
- safe default fallback
- unknown keys removed

Frontend-only config support is NOT acceptable.

---

# 23 / SINGLE SOURCE OF TRUTH

Avoid long-term duplication between:

- JavaScript defaults
- PHP defaults

If practical within the current architecture,
introduce a maintainable synchronization strategy.

At minimum:

- field names must match
- defaults must match
- enum sets must match
- tests must detect drift

Do not allow JS and PHP schemas to evolve independently without verification.

# 26 / DELETION SAFETY

Never allow deletion to generate invalid renderer state.

# 32 / RENDERER REFACTOR

`Welcome.jsx` / `LandingRenderer` must stop being the canonical storage location for editable business copy.

Renderer responsibilities:

- receive normalized config
- render it
- preserve functional form behavior
- render domain-owned portfolio data
- apply semantic layout tokens
- apply semantic motion tokens

Renderer must NOT:

- define editable business lists as static arrays
- define editable principles
- define editable process steps
- define editable transformation rows
- define editable service items
- define editable contact copy

Fallback content belongs in defaults,
not scattered through JSX.
